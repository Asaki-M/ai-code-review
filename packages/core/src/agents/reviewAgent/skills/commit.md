# Commit Message 审查规范

## 准确性
- commit message 应准确概括本次改动的主要目的，不能与实际代码行为冲突。
- 如果改动包含修复、重构、功能新增、配置调整或回滚，应在 message 中体现真实意图，不要使用模糊表述。
- 不要把未实际完成的内容写进 commit message，也不要遗漏会影响理解的重要改动。

## 清晰度
- 优先使用简洁、直接、可读的短句描述改动，避免空泛词汇如 update、fix issues、misc changes。
- 推荐使用统一前缀，如 feat、fix、refactor、chore、docs，但不要为了套格式牺牲语义准确性。
- message 应让不了解上下文的协作者也能快速理解“改了什么、为什么改”。

## 一致性
- commit message 应与 diff 范围匹配，避免“标题很小、改动很大”或“标题很大、实际只改一点”的失配。
- 如果一次提交混入多个不相关改动，应指出提交粒度过大，不要只评价 message 文案本身。
- 如果 message 声称修复某问题，但 diff 无法证明修复成立，应标记为风险或需补充说明。

## 可追踪性
- 涉及 breaking change、数据修复、脚本迁移、安全修复或线上事故处理时，message 应保留足够线索，便于后续追溯。
- 如果项目约定关联 issue、任务号或模块名，应检查是否遵守约定。
- 对自动生成或批量提交信息，检查是否丢失关键上下文，避免影响排查和回滚。
